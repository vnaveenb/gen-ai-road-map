LangChain — fundamentals

Cheat sheet: LangChain is a framework for building LLM applications. Core abstractions: Runnable (the unit of execution), LCEL (composition language), Chains (sequences), Agents (LLM-driven control flow), Tools (callable functions), Memory (state), Retrievers (return docs), VectorStores (similarity search), OutputParsers (structure model output), Callbacks (observability).

What problem does LangChain solve?

LLMs are stateless next-token predictors. Real applications need: prompt templating, structured I/O, tool use, multi-step reasoning, retrieval over private data, conversation memory, observability, and provider abstraction. LangChain provides standardized interfaces for all of these so you can swap models, vector stores, and tools without rewriting the application.

LCEL — the composition layer

LCEL is what makes modern LangChain composable. Every component implements the Runnable protocol, which means you can compose with |:

from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_template("Summarize this: {text}")
model = ChatOpenAI(model="gpt-4o")
parser = StrOutputParser()

chain = prompt | model | parser
result = chain.invoke({"text": "..."})

LCEL gives you for free: streaming, async, batching, parallelism, retries, fallbacks, schema, and LangSmith tracing.

Why use LCEL instead of plain Python?
LCEL standardizes the runtime — every chain gets .stream(), .batch(), .ainvoke(), automatic parallelization with RunnableParallel, automatic retries with .with_retry(), fallbacks with .with_fallbacks(), and full callback/tracing integration. Plain Python gives you none of that without writing it yourself. The cost is a thinner mental model and a slight indirection in debugging.
What's the difference between Runnable, RunnableLambda, RunnableParallel, and RunnablePassthrough?
Runnable is the abstract interface. RunnableLambda wraps a plain Python function into a Runnable so you can pipe it. RunnableParallel takes a dict of Runnables and runs them concurrently, returning a dict — useful when you want to fan out (e.g., retrieve context AND rephrase question in parallel). RunnablePassthrough forwards input unchanged — typically combined with .assign() to enrich a dict without losing the original keys, e.g., RunnablePassthrough.assign(context=retriever).
How do you stream output from an LCEL chain?
Use chain.stream(input) for sync iterator or async for chunk in chain.astream(input) for async. For granular streaming over tool calls and intermediate steps, use astream_events(version="v2") which yields typed events — on_chat_model_stream, on_tool_start, etc. This is what powers production UIs with token-by-token rendering and tool-call indicators.
When would you NOT use LangChain?
For very simple one-shot LLM calls — the abstraction overhead isn't worth it; just use the provider SDK directly. Also when you need ultra-fine control over latency budgets and every millisecond matters — LangChain adds a small but measurable overhead. And when you're building a deeply custom agent loop where LangGraph (the lower-level state machine) is a better fit than LangChain's higher-level agent abstractions.
Gotcha Interviewers will ask: "LangChain has been criticized as bloated and unstable. What's your view?" — Don't get defensive. Acknowledge the criticism: early LangChain had unstable APIs and too many abstractions. Then pivot: since the v0.1+ refactor, langchain-core, langchain, and langchain-community are properly separated; LCEL replaced the old chain hierarchy; and LangGraph emerged for stateful workflows. Today the framework is much leaner and the criticism is dated.

Prompt templates & few-shot prompting

from langchain_core.prompts import FewShotChatMessagePromptTemplate, ChatPromptTemplate

examples = [
    {"input": "2+2", "output": "4"},
    {"input": "3+5", "output": "8"},
]
example_prompt = ChatPromptTemplate.from_messages([
    ("human", "{input}"),
    ("ai", "{output}"),
])
few_shot = FewShotChatMessagePromptTemplate(
    example_prompt=example_prompt,
    examples=examples,
)
final = ChatPromptTemplate.from_messages([
    ("system", "You are a math tutor."),
    few_shot,
    ("human", "{input}"),
])
Static few-shot vs dynamic (semantic) few-shot — when do you use each?
Static is fine when the task is narrow and examples are universally useful. Semantic few-shot (using SemanticSimilarityExampleSelector) selects examples most similar to the current input from a larger pool — essential when you have a wide task distribution and want per-query example relevance. Trade-off: semantic selection adds an embedding call per request, so cost and latency go up. In high-throughput systems, cache the example embeddings and use a small fast embedding model like text-embedding-3-small.

An LLM occasionally returns malformed JSON. How do you handle it in production?
Layered defense: (1) Use with_structured_output() with the provider's native JSON mode or function-calling — eliminates most failures. (2) Wrap in OutputFixingParser as a self-healing layer that re-prompts the model with the parse error. (3) Add a final code-level fallback — try a permissive parser like json5 or extract JSON from text with a regex. (4) Log all parse failures to LangSmith with the raw output for prompt iteration. (5) For high-stakes fields, validate semantically post-parse (e.g., date is in valid range, amount is positive).

LangChain — deep internals

The Runnable protocol — how it really works

Every Runnable implements:

  • invoke(input, config) — synchronous single call
  • ainvoke(input, config) — async single call
  • batch(inputs, config) — parallel batch (uses thread pool by default)
  • abatch(inputs, config) — async parallel batch
  • stream(input, config) — yields chunks
  • astream(input, config) — async chunk yields
  • astream_events(input, config, version) — typed event stream
  • get_input_schema() / get_output_schema() — Pydantic schemas

The config object is critical and often missed:

config = {
    "callbacks": [...],         # observability hooks
    "tags": ["prod", "v2"],     # filterable in LangSmith
    "metadata": {"user_id": ...}, # arbitrary tracing metadata
    "run_name": "my_chain",     # named run for tracing
    "max_concurrency": 5,       # for batch ops
    "configurable": {           # runtime overrides for ConfigurableField
        "llm_temperature": 0.7,
        "session_id": "abc123",
    },
    "recursion_limit": 25,      # max recursive runnable depth
}
What is RunnableConfig and why does it matter at scale?
It's the per-invocation control plane. At scale you use it to: (1) propagate request-scoped metadata (user_id, request_id, tenant) through every nested LLM/tool call for tracing — LangSmith uses this to build the entire span tree; (2) pass runtime config via configurable fields — e.g., switch model temperature per request without rebuilding the chain; (3) control concurrency for batch operations; (4) pass authentication tokens or per-tenant credentials down through callbacks. Forgetting to thread config through custom Runnables breaks tracing — a common production bug.

Callbacks & observability

LangChain's callback system is event-based. Major events:

  • on_chain_start / on_chain_end / on_chain_error
  • on_llm_start / on_llm_new_token / on_llm_end / on_llm_error
  • on_chat_model_start (chat models — distinct from on_llm_start)
  • on_tool_start / on_tool_end / on_tool_error
  • on_retriever_start / on_retriever_end
  • on_agent_action / on_agent_finish
from langchain_core.callbacks import BaseCallbackHandler

class TokenCounter(BaseCallbackHandler):
    def __init__(self): self.tokens = 0
    def on_llm_new_token(self, token, **kw):
        self.tokens += 1

chain.invoke(input, config={"callbacks": [TokenCounter()]})
How does LangSmith tracing actually work under the hood?
LangSmith ships a callback handler (LangChainTracer) auto-registered when LANGCHAIN_TRACING_V2=true. Every Runnable lifecycle event becomes a span. The handler maintains a tree by tracking parent/child run IDs — when a chain calls a tool which calls an LLM, you get nested spans. The data is batched and sent to the LangSmith API asynchronously to avoid blocking. For custom systems (no LangChain), you can call the LangSmith SDK directly with @traceable decorator or context managers.

Custom Runnables

from langchain_core.runnables import RunnableLambda, RunnableConfig

def my_logic(input: dict, config: RunnableConfig) -> dict:
    # ALWAYS accept config as second arg to propagate tracing
    return {"result": process(input)}

Gotcha If your custom Runnable internally calls another Runnable (e.g., an LLM), you MUST thread the config through: inner_chain.invoke(x, config). Otherwise the inner call shows up as a disconnected trace, not a child of your custom runnable. This is one of the most common production observability bugs.

LangGraph — fundamentals

Cheat sheet: LangGraph is a low-level orchestration framework for stateful, multi-actor LLM applications. Think of it as: "LangChain gave you Runnables; LangGraph gives you a state machine of Runnables with checkpointing, human-in-the-loop, and time travel." Built by the LangChain team. The default choice for any agent loop more complex than a single ReAct iteration.

Why LangGraph exists

Classic LangChain agents (AgentExecutor) had problems: hidden control flow, hard to debug, no built-in persistence, no human-in-the-loop, no streaming of agent state, no time travel. LangGraph addresses these by giving you an explicit graph where you control every transition.

Core concepts

ConceptWhat it is
StateGraphThe graph builder. Nodes are functions, edges are transitions.
StateA TypedDict or Pydantic model representing the shared state passed between nodes.
NodeA function that takes state and returns a partial state update (a dict).
EdgeConnection between nodes. Can be unconditional or conditional.
Conditional edgeA function that inspects state and returns the next node name.
ReducerHow updates to a state field are merged (e.g., operator.add appends to a list).
CheckpointerPersists state at each step — enables resume, HITL, time travel.

InterruptPauses execution at a node — for human input or approval.
SendDynamic fan-out to multiple parallel branches (map-reduce pattern).

Minimal example — a ReAct-style agent in LangGraph

from typing import TypedDict, Annotated
from operator import add
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import MemorySaver
from langchain_core.messages import BaseMessage, HumanMessage
from langchain_openai import ChatOpenAI

class AgentState(TypedDict):
    messages: Annotated[list[BaseMessage], add]  # reducer: append

llm = ChatOpenAI(model="gpt-4o").bind_tools([search_tool])

def agent_node(state: AgentState):
    response = llm.invoke(state["messages"])
    return {"messages": [response]}

def tool_node(state: AgentState):
    last = state["messages"][-1]
    results = []
    for call in last.tool_calls:
        result = search_tool.invoke(call["args"])
        results.append(ToolMessage(content=result, tool_call_id=call["id"]))
    return {"messages": results}

def should_continue(state: AgentState) -> str:
    last = state["messages"][-1]
    return "tools" if last.tool_calls else END

graph = StateGraph(AgentState)
graph.add_node("agent", agent_node)
graph.add_node("tools", tool_node)
graph.add_edge(START, "agent")
graph.add_conditional_edges("agent", should_continue, {"tools": "tools", END: END})
graph.add_edge("tools", "agent")

app = graph.compile(checkpointer=MemorySaver())
result = app.invoke(
    {"messages": [HumanMessage("Find me news on AI")]},
    config={"configurable": {"thread_id": "user_42"}}
)
LangGraph ReAct loop — conditional edge from agent decides between tool node or END
What is a reducer in LangGraph and why is the Annotated[list, add] pattern important?
By default, when a node returns a partial state update, that field is replaced. A reducer changes the merge semantics. Annotated[list[BaseMessage], add] tells LangGraph to use operator.add to merge — which for lists means concatenation. So when a node returns {"messages": [new_msg]}, the new message is appended rather than replacing the entire list. Without this, your conversation history would be wiped at every node. Custom reducers handle deduplication, last-write-wins, set semantics, etc. There's also the built-in add_messages reducer which is smarter than plain add — it handles message ID deduplication.
What does checkpointer do, and what backends does LangGraph support?
A checkpointer persists state after every node execution, keyed by thread_id. This enables: (1) resumption — kill the process and resume; (2) human-in-the-loop — pause for human input, persist, resume on response; (3) time travel — replay from any prior checkpoint; (4) multi-turn conversation — automatic memory by passing the same thread_id. Backends: MemorySaver (dev only, in-process), SqliteSaver, PostgresSaver (production default), RedisSaver (community). For production, Postgres with the async AsyncPostgresSaver is the standard.

Human-in-the-loop & interrupts

graph.compile(
    checkpointer=PostgresSaver(...),
    interrupt_before=["sensitive_action"]  # pause before this node
)

# OR within a node:
from langgraph.types import interrupt
def approval_node(state):
    decision = interrupt({"approve_payment": state["amount"]})
    return {"approved": decision}

# Resume with human's input:
app.invoke(Command(resume="yes"), config={"configurable": {"thread_id": "..."}})
When would you use interrupt_before vs the new dynamic interrupt() primitive?
interrupt_before/interrupt_after is static — declared at compile time, pauses unconditionally at that node. Useful for hard-coded checkpoints like "always confirm before deletion". The dynamic interrupt() function pauses mid-node based on runtime conditions — e.g., only ask for human approval if the amount > $10k. It also supports passing structured data to the human and getting structured data back via Command(resume=...). Dynamic is more flexible and is the modern recommended pattern.

Subgraphs & composition

# Build a subgraph for a sub-workflow
retrieval_subgraph = StateGraph(RetrievalState)
retrieval_subgraph.add_node("rewrite", ...)

When state schemas differ between parent and subgraph, what happens?
Two options: (1) Matching keys — overlapping keys flow automatically; non-overlapping subgraph state is invisible to the parent. (2) Different schemas — wrap the subgraph in a node function that transforms parent state → subgraph input → captures subgraph output → returns parent state update. This is the cleaner pattern for genuinely decoupled subgraphs and what you'd describe in a system-design interview.

Send API — map-reduce / dynamic parallelism

from langgraph.types import Send

def fan_out(state):
    # Dynamically dispatch one "process_item" node per item
    return [Send("process_item", {"item": item}) for item in state["items"]]

graph.add_conditional_edges("planner", fan_out, ["process_item"])
graph.add_edge("process_item", "aggregator")

This is how you do map-reduce in LangGraph: dynamically spawn N parallel branches, each operating on a different input, then converge at a downstream node. Used heavily in multi-document analysis, parallel agent evaluation, and batch processing within a single graph run.

Time travel

# Get history of all checkpoints for a thread
for snap in app.get_state_history(config):
    print(snap.values, snap.next, snap.config)

# Rewind: fork from a past checkpoint
past_config = snap.config  # from history

Give a real use case for time travel in production.
Debugging non-deterministic agent failures. An agent makes a bad tool call and ends in a bad state. With time travel, you can rewind to the checkpoint just before the bad call, modify the state (e.g., add a guidance message), and re-run from there to see if your fix would have worked — without re-doing the entire conversation. Also valuable for user-facing "undo last action" features in agent UIs.

Persistence layer architecture

from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

async with AsyncPostgresSaver.from_conn_string("postgresql://...") as checkpointer:
    await checkpointer.setup()  # creates tables
    app = graph.compile(checkpointer=checkpointer)

Postgres tables created: checkpoints, checkpoint_writes, checkpoint_blobs. State is JSON-serialized and stored per (thread_id, checkpoint_id). For high-throughput systems, partition by thread_id and add TTL cleanup.

Gotcha Pydantic objects with non-JSON-serializable types (datetime, custom classes) break the default checkpointer serializer. Either: (1) use simple types in state, (2) provide a custom JsonPlusSerializer with pickle_fallback=True, or (3) make all custom classes Pydantic models with JSON-mode serialization.

Multi-agent patterns in LangGraph

1. Supervisor pattern

A central LLM ("supervisor") routes work to specialized worker agents. Each worker returns to the supervisor.

Supervisor pattern — central router with specialist workers

2. Hierarchical (teams of teams)

Multiple supervisors, each managing a team. A top-level supervisor routes between teams. Used in the LRA-style enterprise systems.

3. Swarm / network

Agents hand off directly to each other (peer-to-peer) without a central supervisor. Each agent has a list of agents it can hand off to. Looser coupling, harder to control.

4. Pipeline / sequential

Linear chain: agent A → agent B → agent C. Simplest. Use when there's no branching.

When would you choose a swarm over a supervisor?
Swarm when the routing logic is too complex or too context-dependent to centralize, and each specialist agent has enough context to know when to hand off. Example: a customer support swarm where the "billing agent" knows to hand off to "refund agent" when refund is mentioned. Supervisor when you want centralized control, observability, and policy enforcement (rate limits, content filters, budget caps). In enterprise, supervisor wins almost always — it's auditable. Swarm wins for creative/exploratory tasks.

Production & scale issues

Latency optimization

  • Parallelize independent steps via RunnableParallel — e.g., embed query AND fetch user profile concurrently.
  • Stream tokens to the user — perceived latency drops dramatically; first-token latency < 500ms is the target.
  • Cache: prompt caching at the model level (Anthropic prompt caching, OpenAI prompt caching), semantic caching for embeddings (GPTCache, Redis), exact-match LLM response caching for FAQ-style queries.
  • Smaller models for triage: use Haiku/gpt-4o-mini to classify intent or extract entities, only escalate to Opus/gpt-4o for complex reasoning.
  • Batch embedding calls — never embed one chunk at a time.
  • Async everywhere — synchronous I/O kills concurrency.

Cost optimization

  • Token accounting: instrument on_llm_end callback to track tokens per request, per user, per route.
  • Prompt caching: Anthropic offers up to 90% cost reduction on cached prefix tokens, OpenAI ~50%. Critical for long system prompts and few-shot examples.
  • Model routing: cheap models for simple tasks. A router LLM (small) classifies query, dispatches to right model.
  • Set hard token budgets per request with max_tokens and trim context aggressively.
  • Compress retrieved chunks before sending to LLM (e.g., ContextualCompressionRetriever with LLM-based compressor — but watch: this adds an LLM call, so only worth it when downstream context is expensive).

Reliability patterns

  • .with_retry(stop_after_attempt=3, wait_exponential_jitter=True) — exponential backoff on transient failures.
  • .with_fallbacks([backup_chain]) — if primary fails, try fallback. Use for cross-provider failover (OpenAI → Anthropic).
  • Circuit breakers at the gateway level (LiteLLM, Portkey) — stop hammering a degraded provider.
  • Idempotency keys for non-deterministic tool calls.
  • Dead-letter queues for failed agent runs — replay later from checkpoint.

RAG architecture & patterns

Cheat sheet: RAG = Retrieval-Augmented Generation. Solves: LLM hallucination, stale knowledge, lack of access to private data, citation requirements. Pipeline: ingest → chunk → embed → store → retrieve → (rerank) → generate. The architecture is simple; the engineering is in chunking, embedding choice, retrieval strategy, and evaluation.

How do you pick chunk size?
Start with three principles: (1) chunks must fit context comfortably — for retrieval of top-5 with reranking and a system prompt, ~512 tokens × 5 = 2.5k is typical; (2) chunks must be self-contained — too small and you lose context, too large and you dilute relevance; (3) align with embedding model limits — most embedders max at 512–8192 tokens. Then measure: build a small golden set (50–100 query/answer pairs), evaluate retrieval recall@K and answer faithfulness across chunk sizes 256, 512, 1024. Pick the sweet spot. For most enterprise docs, 512 tokens with 50–100 token overlap is the strong default.
What's the difference between parent-document retriever and sentence-window retriever?
Both index small units and return larger contexts. Parent-document chunks the document twice — small chunks for embedding and large parent chunks for context; on retrieval, it finds the small chunk and returns its parent. Sentence-window indexes individual sentences but returns the sentence plus its surrounding window (N sentences before/after). Sentence-window is finer-grained and works well when answers depend on very specific phrasing; parent-document is coarser and better when answers span a few paragraphs. Both fix the trade-off between retrieval precision and context richness.

Retrieval deep dive

Similarity metrics

  • Cosine similarity: angle between vectors. Default for normalized embeddings. Range [-1, 1].
  • Dot product: equivalent to cosine when vectors are unit-normalized. Used when not normalized (e.g., embeddings with magnitude information).
  • Euclidean (L2): distance. Less common in modern embedders.

ANN indexes

IndexTrade-off
Flat (exact)Slow, 100% accurate. Small datasets only.
HNSWGraph-based. Fast queries, high memory, slow build. Modern default.
IVFCluster-based. Lower memory, tunable accuracy via nprobe.
IVFPQIVF + product quantization. Lowest memory, accuracy hit.
ScaNNGoogle's tree-AH hybrid. Used in Vertex AI Vector Search.
DiskANNSSD-based; near-DRAM speed at SSD cost. For billion-scale.

Hybrid search (dense + sparse)

Dense embeddings capture semantics but miss exact terms (product codes, names, rare words). Sparse retrieval (BM25, SPLADE) captures lexical matches. Hybrid combines both, fusing rankings.

Common fusion methods:

  • Reciprocal Rank Fusion (RRF): score = Σ 1/(k + rank_i). Simple, no calibration needed. Default choice.
  • Weighted score fusion: α * dense_score + (1-α) * sparse_score. Needs score normalization.
  • Learning-to-rank: train a model to combine signals. Heavy machinery; only when you have labels.

Reranking

Retrieve top-K candidates (large K, e.g. 50), then a cross-encoder reranker scores (query, doc) pairs and returns top-N (e.g., 5). Cross-encoders are slower per pair but much more accurate than bi-encoder similarity.

Query transformations

  • Multi-query: generate N rephrasings of the user query, retrieve for each, deduplicate. Boosts recall.
  • HyDE (Hypothetical Document Embeddings): ask the LLM to write a hypothetical answer to the query; embed the hypothetical answer instead of the query. Often outperforms raw query embedding for short queries.
  • Step-back prompting: ask a more abstract version of the question first to retrieve broader context.
  • Sub-question decomposition: split a complex question into sub-questions, retrieve for each, answer separately, synthesize.
  • Query routing: classify the query and route to a specialized retriever (legal vs HR vs financial corpus).
Walk me through your retrieval optimization playbook.
In order of effort vs gain: (1) get the basics right — chunk size 512, overlap 50–100, recursive splitter, embedding task_type set correctly; (2) add a reranker — biggest single quality jump for the least effort; (3) hybrid search — adds 10–20% recall on technical/named-entity-heavy corpora; (4) query rewriting/multi-query — helps recall when users write terse queries; (5) parent-document or sentence-window — when chunks are too small to be self-contained; (6) metadata filtering — exclude irrelevant documents pre-retrieval (date, source, tenant); (7) finetune the embedding model on your domain — last resort, big effort, marginal gain unless your domain is very specialized.
Gotcha A favorite trap: "How does the LLM know which retrieved chunks are actually relevant?" — It doesn't, robustly. That's why you (a) rerank to prune noise, (b) prompt with explicit instructions to ignore irrelevant context and say "I don't know", (c) evaluate faithfulness post-hoc. The chunk count you send to the LLM is a knob: too few = recall misses; too many = noise drowns signal. Empirically, 3–7 chunks with a strong reranker is the sweet spot for most QA tasks.

  2. For each, manually (or with an LLM + human review) write the ideal answer and identify the source chunks.

LLM-as-judge isn't perfect. How do you trust it?
Calibrate it. Have humans label 50–100 examples yourself. Run the LLM judge on those. Measure judge agreement with humans (e.g., Cohen's kappa or simple accuracy). If agreement is low (< 0.6), the judge prompt needs work — make it more specific, give it rubrics, use chain-of-thought scoring. Use multiple judges and majority-vote for high-stakes evals. Advanced RAG (LRA, GraphRAG, Agentic RAG)

Long-context RAG (LRA)

Modern models support 200k–2M token contexts (Claude 3.5/4, Gemini 1.5/2.0). LRA is RAG that exploits this: retrieve more chunks (or whole documents), put it all in context, let the model figure it out. Your LRA system on Azure OpenAI GPT-4 is in this family.

When LRA wins:

  • The corpus is bounded (e.g., one course's materials, one contract).
  • Reasoning needs cross-document synthesis.
  • Cost is acceptable (long context = many tokens).

When classic RAG still wins:

  • Corpus is huge (10M+ docs).
  • Need precise citations to small spans.
  • Latency budget is tight.
  • Costs need to stay low at high QPS.

Hybrid (best of both): Use embedding retrieval to narrow from corpus to ~50–500 candidate chunks, then put all of those in long context. This is the practical LRA pattern.

GraphRAG

Microsoft's pattern (and an industry trend in late 2024–2025): extract entities and relationships from documents → build a knowledge graph → cluster nodes into community summaries → at query time, retrieve via graph traversal + community summaries instead of just vector similarity.

Strengths: handles "global" questions that span the corpus ("what are the main themes?"), better at multi-hop reasoning.
Weaknesses: expensive to build (every chunk needs entity/relation extraction), heavy infrastructure, harder to update incrementally.

Agentic RAG

Instead of one-shot retrieve-then-generate, an agent iteratively retrieves: it can rephrase the query, retrieve, evaluate sufficiency, retrieve again, decompose into sub-queries, etc. Each step is a tool call. LangGraph is the natural orchestration layer.

Agentic RAG — planner decides; retrieval + grading loop; fallback to web search; generate

Known pattern names: Self-RAG (model emits reflection tokens), Corrective RAG (CRAG) (retrieve → grade → fallback to web if low confidence), RAG-Fusion (multi-query + RRF), ReAct-RAG.

Agent fundamentals

Cheat sheet: An "agent" is an LLM that decides what to do next from a set of options (tools, sub-agents, terminate). Key ingredients: a system prompt defining behavior, a tool schema the model can emit, a loop that executes tool calls and feeds results back, and a termination condition. Modern reality: most production "agents" are constrained, well-prompted state machines — not free-roaming AGI.

Anatomy of an agent

  1. System prompt — role, capabilities, constraints, output format.
  2. Tool registry — set of functions with name, description, input schema (JSON schema or Pydantic).
  3. State — conversation history, scratchpad, intermediate results.
  4. Loop — call LLM with messages + tool list → if LLM emits tool call, execute, append result, loop; if LLM emits final answer, return.
  5. Stop conditions — final answer, max iterations, error, human interrupt, budget exhausted.

Tool design rules
  • Name — verb-noun, lowercase, unambiguous.
  • Description — what it does, when to use it, when NOT to use it. The model decides based on this; treat it as a prompt.
  • Args — minimal, well-typed, with descriptions and constraints.
  • Output — structured, predictable, error-handled. Never raise — return structured errors the LLM can read.
  • Idempotent when possible — agents retry.
  • Side effects require explicit confirmation flow (human-in-the-loop).

Tool errors & the agent loop

When a tool errors, you have three options:

  1. Return the error as a tool message — let the LLM see it and self-correct. Best for recoverable errors (wrong arg, no results).
  2. Retry with backoff — transient errors (rate limit, network).
  3. Escalate — unrecoverable; terminate or hand off to human.
An agent enters an infinite loop calling the same tool. What's your debug strategy?
First, add a circuit breaker — max iterations, max identical consecutive tool calls. Then root-cause: (1) inspect the trace — most often, the tool returns ambiguous output the model can't parse, so it keeps trying; (2) check the tool's description — vague descriptions cause confusion; (3) check the tool's output — return clear "no results" rather than empty strings; (4) check the system prompt — does it tell the agent what to do when stuck? Usually the fix is in tool description + output format, not in the agent loop itself.
How do you control agent cost and prevent runaway spending?
Layered controls: (1) recursion_limit in LangGraph caps node executions; (2) per-thread token budget tracked in state — abort if exceeded; (3) provider-level rate limits + spending caps (OpenAI dashboard, AWS budget alerts); (4) routing — cheap model for triage, expensive only for hard steps; (5) prompt caching for stable system prompts; (6) tool-call quotas — max N calls of an expensive tool per session; (7) production monitoring — alert on per-user cost outliers in LangSmith or your tracing layer.

Model Context Protocol (MCP)

Cheat sheet: MCP (Model Context Protocol) is an open protocol introduced by Anthropic in late 2024 for connecting LLM applications to external data sources and tools. Think USB-C for AI: standardized client-server protocol so an MCP server (e.g., GitHub, Slack, your enterprise DB) can be plugged into any MCP-compatible client (Claude Desktop, your custom app, etc.) without bespoke integration. Adopted by OpenAI, Google, and the broader ecosystem in 2025.

MCP architecture

Three roles:

  • Host — the application (e.g., Claude Desktop, your agent app).
  • Client — embedded in the host, talks one-to-one to a server.
  • Server — exposes tools, resources, prompts.

Three primitives a server can expose:

  • Tools — callable functions (model-controlled).
  • Resources — data the LLM can read (file contents, DB rows; application-controlled).
  • Prompts — reusable prompt templates (user-controlled, e.g., slash commands).

Transport

  • stdio — for local servers spawned as subprocesses.
  • HTTP with SSE / streamable HTTP — for remote servers. Streamable HTTP is the modern default.

Why MCP matters for senior interviews

  1. It's the standardization layer for tool integration. Before MCP, every framework had its own tool protocol — LangChain tools, OpenAI functions, Anthropic tools, etc. MCP lets you write once, use anywhere.
  2. Enterprise adoption is rapid: MCP servers for GitHub, Slack, Postgres, Google Drive, Jira are off-the-shelf.
  3. It enables tool ecosystems — third-party servers for SaaS, internal teams expose their systems via MCP for any AI app to use.
  4. Security model is taken seriously: capabilities, consent, scoped access — important for compliance discussions.

LangChain ↔ MCP

langchain-mcp-adapters wraps MCP tools into LangChain tools, so you can use MCP servers inside LangGraph agents. This is the pattern your LRA system uses.

How does MCP differ from OpenAI function calling?
Function calling is a model-level capability — the LLM outputs structured tool calls. MCP is a transport/protocol layer — it standardizes how an application discovers and invokes tools from external servers. They're complementary: an MCP server exposes tools that ultimately get surfaced to the LLM via function calling. MCP also adds resources (read-only data) and prompts (reusable templates), which function calling doesn't cover. The other key difference: MCP servers can be developed and deployed independently — you can plug Anthropic's official GitHub MCP server into any MCP-compatible host without writing integration code.
Security concerns with MCP?
Several. (1) Prompt injection via tool descriptions or resource content — an attacker-controlled MCP server can craft tool descriptions that hijack the agent. (2) Confused deputy — the agent has more privileges than the user; a malicious server can trick the agent into operations the user shouldn't be able to do. (3) Data exfiltration — a malicious server could return content designed to make the agent send sensitive data to another tool. Mitigations: capability scoping per server, user consent prompts for sensitive operations, sandboxing, content filtering on tool descriptions, and treating tool output as untrusted input.

Computer use & 2025-26 agentic developments

Computer-use agents

Anthropic released "computer use" in Oct 2024 with Claude 3.5 Sonnet — a model trained to view screenshots of a desktop and emit mouse/keyboard actions.   3. Model outputs an action: click(x, y), type(text), scroll, key(combo).

If MCP standardizes tool integration, why would I still need LangGraph?
MCP is the transport — how tools get to the model. LangGraph is the orchestration — how the agent decides what to do across many steps with state, branches, persistence, and human-in-the-loop. You need both: MCP plugs in your tools, LangGraph orchestrates the agent loop. Think of MCP as the I/O layer and LangGraph as the control layer.
What's your view on computer use vs traditional API integration?
API integration is always preferable when available — faster, cheaper, more reliable, auditable. Computer use is the right answer when no API exists or when the API is incomplete and the workflow is locked behind a UI. Real enterprise use cases: legacy systems with no API surface, vendor portals, internal tools the team won't expose programmatically. The pragmatic stance: prefer MCP + APIs by default; reach for computer use as a last resort, in a sandbox, with clear human oversight, and only for non-critical workflows initially.

Fine-tuning fundamentals

Cheat sheet: Fine-tuning adapts a pretrained model to a specific task or domain. Approaches: full fine-tuning (update all weights), parameter-efficient (LoRA/QLoRA — update small adapter matrices), instruction tuning (SFT), preference tuning (RLHF, DPO). Choose based on task, data size, compute budget. Rule of thumb: try prompting → few-shot → RAG → fine-tuning, in that order. Fine-tune only when prompting can't get you there.

Stages

  • Pretraining — next-token prediction on internet-scale text. Done by frontier labs.
  • Supervised fine-tuning (SFT) — train on instruction → response pairs. Adapts base model to task.
  • Preference tuning — RLHF, DPO, ORPO. Align responses with human preferences.

  • Quality > quantity. 500 great examples beat 50k mediocre ones.
  • Format consistency — every example uses the same template.
  • Diversity — cover the input distribution.
  • Validation split (5–10%) and held-out test set.
  • Deduplicate aggressively — memorization risk.
  • PII redaction, consent, license compliance.

LoRA / QLoRA deep dive

The intuition

Full fine-tuning updates billions of parameters. LoRA observes that the update to the weight matrix is low-rank — it can be represented as the product of two small matrices A and B.

For a weight matrix W (d × k), instead of computing W' = W + ΔW where ΔW is full-rank, we approximate ΔW ≈ B·A where A is r×k and B is d×r, with r much smaller than d, k (typically r = 8, 16, 32, 64).

At training: freeze W, learn A and B. Parameter count drops from d·k to r·(d+k) — orders of magnitude smaller.

At inference: either keep adapters separate (swap per task) or merge W_merged = W + B·A for zero overhead.

Key hyperparameters

QLoRA

QLoRA = Quantized LoRA. Three innovations:

  1. 4-bit NF4 quantization of the base model — fits 70B in 48GB VRAM.
  2. Double quantization — quantize the quantization constants themselves.
  3. Paged optimizers — use NVIDIA unified memory to handle optimizer state spikes.

LoRA adapters stay in higher precision (bf16) and accumulate gradients normally. Result: comparable quality to full fine-tuning at a fraction of memory.

Why does LoRA work? Theoretical justification?
The hypothesis (from the LoRA paper) is that pretrained models have a low intrinsic dimension for downstream task adaptation — there's a low-rank manifold in weight space that captures most useful updates. Empirically, even rank 1–8 LoRA often matches full fine-tuning. The reason is that pretraining puts the model in a region of weight space where most directions are already useful; you only need to gently nudge it. Higher rank doesn't always help — past a point you're just adding noise.
When does LoRA underperform full fine-tuning?
Three cases: (1) The task is very different from pretraining — large domain shift needs capacity LoRA may not have at moderate rank. (2) The training set is very large — full FT can absorb more signal. (3) You need to forget something — full FT can override pretrained behavior; LoRA only adds. Mitigation: increase rank, target more modules (include MLP not just attention), or move to a hybrid approach.
How do you serve a LoRA-fine-tuned model in production?
Two options: (1) Merged inference — merge LoRA into base weights at load time, deploy as a single fine-tuned model. Best for one-task deployments. (2) Multi-adapter inference — keep base model loaded once, swap LoRA adapters per request. vLLM, S-LoRA, and TGI support this. Best for SaaS where you have a fine-tune per customer/use-case. Memory grows by adapter size, not base size — you can serve hundreds of LoRAs from one GPU. On Vertex AI, you'd typically deploy via custom container with vLLM, or use Vertex's managed model garden for supported base models.

RLHF, DPO, alignment

RLHF (Reinforcement Learning from Human Feedback)

  1. SFT — fine-tune the base model on instruction data.
  2. Reward model (RM) — collect preference data (pairs: prompt + chosen response + rejected response). Train a model to score responses.
  3. RL — use PPO (Proximal Policy Optimization) to optimize the SFT model against the RM, with a KL penalty to prevent drifting too far from SFT.

Painful: needs PPO infrastructure, reward hacking is real, hyperparameter sensitivity.

DPO (Direct Preference Optimization)

Bypasses the RM entirely. Re-parameterizes the RLHF objective so you can train directly on preference pairs using a simple classification loss. Simpler, more stable, comparable results.

from trl import DPOTrainer, DPOConfig

dpo_trainer = DPOTrainer(
    model=model,
    ref_model=reference_model,  # frozen SFT model
    args=DPOConfig(beta=0.1, ...),
    train_dataset=preference_dataset,  # cols: prompt, chosen, rejected
    tokenizer=tokenizer,
)
dpo_trainer.train()

The beta hyperparameter controls how much the model can drift from the reference. Lower beta = more drift allowed.

Other preference methods

  • ORPO — combines SFT and preference optimization in one stage. No reference model needed.
  • KTO (Kahneman-Tversky) — works with binary good/bad signals, no need for pairs.
  • SimPO — simpler than DPO, no reference model.
Why DPO over RLHF?
DPO replaces a three-stage process (SFT → RM → PPO) with a single fine-tuning step using preference pairs. No reward model to train, no PPO instability, no reward hacking, much less compute. The downside: you lose the explicit reward signal which can be reused or interpreted; you also lose the ability to do online RL with continuous feedback. For most enterprise alignment work, DPO is the right starting point; RLHF if you're a frontier lab.

Why vLLM has higher throughput than naive transformers serving?
Three reasons. (1) PagedAttention — KV cache is paged like virtual memory, eliminating fragmentation; you can pack many more concurrent sequences in the same VRAM. Capacity sketch

  • 10k users × 5 queries/day = 50k queries/day ≈ 0.6 QPS average, ~5 QPS peak.

  • Embedding cost: 5M docs × 1000 tokens × $0.025/M = ~$125 one-time.
  • Per query: ~200 input tokens (query) + 4k context (retrieved) + 500 output. At Gemini Pro pricing roughly <$0.005/query. 50k × $0.005 = $250/day. Reasonable.
  • Latency budget: embed query (50ms) + retrieve (100ms) + rerank top-50 (200ms) + LLM TTFT (800ms) + stream completion (1500ms) ≈ 2.6s p50. Well within 4s.

Failure modes & mitigations

  • LLM provider outage → fallback to second provider via .with_fallbacks([backup]).
  • Vector store cold → preload index, health checks, fallback to BM25-only retrieval.
  • Rerank pod scaling lag → degrade to no-rerank (more chunks, lower quality but available).
  • Bad model deploy → canary, auto-rollback on faithfulness regression.
  • Hot tenant overload → per-tenant rate limits at gateway.
  • Prompt injection → input filter, output filter, separate "untrusted retrieval" from "system instructions" in prompt.

Scaling LLM workloads

Throughput levers

  • Continuous batching in serving — vLLM, TGI.
  • Speculative decoding — small draft model proposes tokens, big model verifies. 2–3x speedup.
  • Quantization — INT8 / FP8 / AWQ / GPTQ. Modest quality loss, 2x+ throughput.
  • Tensor parallelism across GPUs for big models.
  • KV cache reuse — prompt caching (Anthropic, OpenAI), automatic in vLLM via PrefixCache.
  • Compile — torch.compile, TensorRT.

Latency levers

  • Stream tokens — perceived latency drops >50%.
  • First-token target: under 800ms for chat UIs.
  • Parallelize retrieval and prompt assembly with embedding.
  • Smaller model for short-output tasks (classification, routing).
  • Cache: prompt prefix (system + few-shot), exact-match responses, semantic-cache near-duplicate queries.
  • Reduce context: rerank to fewer chunks, summarize old conversation turns.

Reliability

  • Multi-region deploy for high availability.
  • Active-active across providers via a router (LiteLLM, Portkey) for failover.
  • Circuit breakers on provider errors.
  • Async ingestion with dead-letter queue for failed docs.
  • Idempotent tool calls.

Cost & latency optimization

Cost ladder (cheapest first)

  1. Use the smallest model that meets quality. Always benchmark cheap-first.
  2. Prompt cache the stable system prompt and few-shot block.
  3. Compress retrieved context (re-rank to top-3, summarize older turns).
  4. Batch when possible (embeddings, evals).
  5. Use semantic cache for common queries.
  6. Route by complexity — triage with a cheap model, escalate only when needed.
  7. Self-host open-weight models when QPS is high (break-even calculation: typical at > 100k requests/day on a single GPU).

Quick TCO mental model

Self-host break-even: an A100 80GB on GCP is roughly $3–4/hr on-demand, $1.5–2/hr with committed use, so ~$1k–$3k/month for one GPU. That's ~600M tokens/month of Gemini Pro at Vertex AI price, or ~2B+ tokens/month of cheap models. If your workload exceeds that and is consistent, self-host. If bursty or low-volume, managed wins.

How do you decide between fine-tuning and longer prompts?
Three axes. (1) Cost: if the same long prompt is sent millions of times, fine-tuning amortizes — once you've trained, every inference is cheaper. Below that, prompt caching covers most of the gain. (2) Quality ceiling: if behavior can't be coaxed via prompt (very specific style, format, internal vocabulary), fine-tuning. (3) Operational: fine-tuning adds a model lifecycle to maintain, retraining on new data, version pinning. For most enterprises in 2025-26, prompt + cache + structured output is the right answer. Fine-tune only when the math clearly works out.

Q&A drill — LRA

Why LangGraph and not just a LangChain chain?
Three reasons specific to this problem. (1) The review of each criterion is a conditional, multi-step process — retrieve, validate, cite, sometimes loop back — that's a state machine, not a linear chain. (2) HITL is first-class — reviewers must approve before write-back, and the system needs to resume from that checkpoint. LangGraph's interrupt() and checkpointers handle this; LangChain's classic AgentExecutor doesn't. (3) Independent criteria can be processed in parallel via the Send API, then aggregated — natural map-reduce in LangGraph.
Why Azure OpenAI GPT-4 specifically, and not Gemini on Vertex (since you're on GCP)?
Two reasons. (1) Enterprise contract: the org had an existing Azure OpenAI agreement covering data residency, DPIA, and security review — Gemini would have required a new procurement cycle. (2) Long-context behavior: at the time we built it, GPT-4's 32k/128k variants had stronger structured-output reliability for our schema; Gemini's long-context was promising but less battle-tested in our internal benchmarks. We made the architecture provider-agnostic — Azure OpenAI is configured via LangChain's AzureChatOpenAI — so swapping to Gemini Pro is a config change. The MCP layer, embeddings, vector search, and orchestration are all Vertex/GCP-native.
What does MCP give you here that a regular LangChain SharePoint connector wouldn't?
Three things. (1) Decoupling: the MCP server is a separate process owned by the integration team; the AI team consumes tools without owning SharePoint auth or schema. (2) Reusability: the same MCP server is used by other internal AI apps — analytics chatbot, content search — without duplicating connector code. (3) Discoverability + governance: MCP servers expose typed tools and resources with metadata; security review happens at the MCP boundary once. We use langchain-mcp-adapters to surface MCP tools into the LangGraph agents.
How did you measure the 65% review-time reduction?
Pre/post study. Baseline: tracked reviewer time-on-task in the LMS for 30 courses over a quarter, average ~4 hours per course. Post-deployment: same metric for 30 courses, average ~1.4 hours per course (reviewers now verify and resolve LLM verdicts rather than reading from scratch). Adjusted for course complexity (page count) using a regression to avoid skew. Independently, we tracked reviewer agreement with the LLM verdict by criterion to ensure quality didn't degrade — agreement > 88% after the second iteration of prompts, and we treated criteria with < 80% agreement as "advisory only" until improved.
How do you prevent the LLM from fabricating citations?
Four layers. (1) Validation Agent is told it must output citations as {chunk_id, exact_quoted_span} in a Pydantic schema; the prompt forbids paraphrasing in the span. (2) Citation Agent runs a separate verification step — it programmatically searches each cited span against the source chunk text; mismatches force a re-run of the Validation Agent with the failed citation flagged. (3) Schema validation rejects responses without at least one verifiable citation when the verdict is pass. (4) Sampling-based eval: 10% of runs are spot-checked by a reviewer, with discrepancies feeding into prompt iteration. Result is essentially zero unverified citations in the final report.
How do you handle a course with 800 pages? Does it fit in GPT-4's context?
We don't put 800 pages into context — that's where the "RAG" in LRA matters. Per criterion, we retrieve only the relevant chunks (typically 5–20 after reranking), which fits comfortably in even 32k context. The "long context" advantage of GPT-4 lets us include richer surrounding context per chunk (parent-document pattern — small chunks for retrieval, paragraph-level parents for context) and process multiple related criteria in a single call when they share retrieval. For criteria that genuinely need to scan the whole course (e.g., "is the learning outcome covered in the assessment?"), we use a hierarchical summarization: chunk-level summaries → section summaries → course summary, then reason at the appropriate level.
What was your hardest bug or failure mode in this system?
Two stand out. Schema drift: GPT-4 occasionally returned valid JSON that didn't satisfy our Pydantic constraints — fields missing or wrong types under load. Fix: switched from JSON-mode prompts to native tool-calling (with_structured_output(method="function_calling")) which enforces schema at the API level, plus an OutputFixingParser as a safety net. Cross-tenant leakage in retrieval: in early staging, a query for course A occasionally retrieved chunks from course B because metadata filters were applied client-side and a query path bypassed them. Fix: enforced filters server-side at the vector store (Vertex AI Vector Search namespaces per course) and added an integration test that explicitly tries to retrieve cross-course and expects zero results.
If I gave you 10x the budget and 10x the corpus, what would you change?
Probably four moves. (1) Move validation off GPT-4 onto a fine-tuned Gemini or Claude with our golden set — better calibrated to our criteria, lower per-call cost. (2) Introduce agentic RAG for the harder criteria where one retrieval pass isn't enough — let the agent rewrite and re-retrieve until it has sufficient evidence. (3) Add a graph layer: course → modules → learning outcomes → assessments — many DQC criteria are inherently relational, and GraphRAG would handle them better than vector-only. (4) Self-host the reranker and a fallback open-weight LLM on GKE to insulate against provider outages and reduce per-query cost at high QPS.

Q&A drill — AR Email Agent

Why not just fine-tune a classifier?

The 2-point gain wasn't worth the operational tax — retraining on label drift, model hosting, MLOps pipeline, slower iteration on category changes. Prompts are versioned in git and pushed in minutes; the classifier evolves as fast as the business. We'd revisit fine-tuning if accuracy plateaued or if costs at scale warranted it.
How do you prevent the agent from sending a wrong auto-reply?

(2) Policy guard — separate LLM pass with a checklist (no PII echoing, no commitments outside policy, tone matches template). (3) Idempotency — emails are processed exactly once via Pub/Sub dedup + DB unique key on message_id. (4) Human shadow — for the first 60 days, every "auto-reply" was actually queued for analyst approval; we measured agreement and gradually relaxed thresholds per category as data accumulated. (5) Kill switch — feature flag to turn off auto-reply globally.
How do you handle multilingual emails?

The knowledge base is in English but Gemini cross-lingual retrieval works (we use the multilingual embedding model so the query embedding doesn't need translation). The ERP MCP server has health checks. On outage detection, the orchestration graph routes those emails into a degraded path — classify only, hold for analyst, mark with "ERP unavailable" so the analyst knows to retry. Pub/Sub redelivery handles transient errors with exponential backoff. We don't fabricate ERP data under any failure mode — that was an explicit design constraint from compliance.

Project 3 — Invoice OCR & Extraction Pipeline

Resume claim: "Built an automated invoice extraction pipeline using pdfplumber, pytesseract, and Llama-3, with an agent-based validation layer, achieving 96% field-level accuracy and producing ERP-ready JSON."
Document-AI-style project. Important angle: the hybrid of OCR + LLM extraction with agentic validation.

The problem

Vendor invoices arrive as PDFs (born-digital and scanned), wildly inconsistent layouts. The ERP needs structured fields — vendor name, vendor ID, invoice number, invoice date, due date, line items (description, qty, unit_price, total), subtotal, tax, total, currency, PO reference, payment terms. Old systems use template matching per vendor and break whenever vendors change layout.

Architecture

Invoice pipeline — hybrid OCR (pdfplumber / pytesseract), Llama-3 structured extraction, LangGraph validation agent with math/vendor/PO checks and focused re-extraction loop.

How data flows (and the role of each component)

  • Ingress: invoices uploaded to GCS bucket (or pushed from email scrape). Cloud Function triggers the pipeline.
  • OCR routing: A classifier (cheap heuristic — does pdfplumber return non-trivial text from page 1?) decides between pdfplumber (born-digital, preserves table structure and bboxes) or pytesseract with image preprocessing (binarize, deskew) for scanned. We also evaluated Vertex Document AI as a third path for complex layouts — used selectively because cost > pytesseract.
  • Text + layout assembly: each line of text retains its bounding box and page; tables retained as structured rows where possible. This layout context is included in the Llama-3 prompt — pure flat text hurts extraction accuracy.
  • Extraction: Llama-3 8B self-hosted via vLLM on a Vertex AI Endpoint (L4 GPU). Prompted with the Pydantic schema for the InvoiceModel and the parsed text+layout. We use vLLM's guided decoding (outlines / guidance) to force valid JSON matching the schema — eliminates malformed-JSON retries.
  • Validation Agent (LangGraph): takes the initial JSON and runs deterministic checks in parallel:
    • Math: sum(line_items) + tax == subtotal? line_total == qty × unit_price?
    • Vendor match: fuzzy match against ERP vendor master; if no hit above threshold, flag.
    • PO reconciliation: each invoice line maps to a PO line (item code + qty within tolerance)?
    • Date sanity: invoice_date <= due_date; both within plausible range.
    • Currency match: matches vendor's contract currency.
    Failures route back to a focused re-extraction — the agent re-prompts Llama-3 with the specific failure and the relevant text region: "You extracted line 3 unit_price as 12.50 but qty × unit_price (5 × 12.50 = 62.50) doesn't match line_total (65.00). Re-examine the page region near 'Item X' and correct."
  • Disposition: passing JSON is posted to SAP via the ERP MCP server (IDoc creation or OData post depending on doc type). Failing JSON (after re-extraction limit) goes to the exception queue with the parsed text and the LLM's last attempt for analyst review.

Training & deployment on Vertex AI / GCP

  • Model: Llama-3 8B Instruct, off-the-shelf (no fine-tuning) — the JSON-mode structured output + good prompting was sufficient for the 96% accuracy target. We explored a LoRA fine-tune on ~1500 labeled invoices but the gain was marginal vs. better prompting + validation, and the operational overhead wasn't worth it.
  • Serving: vLLM in a custom container on Vertex AI Endpoint, L4 GPU, autoscale 1–3. Continuous batching handles bursty load (month-end is 5x average).
  • Validation agent: Cloud Run service running the LangGraph pipeline.
  • Pipeline orchestration: per-document state machine in LangGraph with checkpointing on AlloyDB; allows resume from any stage if a step fails.
  • Eval & monitoring: labeled set of 500 invoices held out for nightly accuracy regression; field-level F1 tracked per vendor and per field (date, amount, line items separately). Drift detection on vendor distribution catches new layouts that need attention.
  • Storage: source PDFs and extraction artifacts in GCS with lifecycle to coldline after 90 days; structured outputs in BigQuery for analytics.

Q&A drill — Invoice Pipeline

Why hybrid OCR (pdfplumber + pytesseract) rather than one tool?
Born-digital invoices (~70% of our volume) have selectable text and explicit table structure — pdfplumber gives near-perfect extraction with bboxes and table grids for free, no OCR error. Scanned invoices (~30%) have no embedded text — pytesseract is needed. Routing between them is a one-line check. Using OCR on born-digital introduces error where none existed; using pdfplumber on scanned returns nothing. The hybrid is the most accurate and cheapest combination. We also have Vertex Document AI in reserve for the long-tail of complex multi-column layouts where both fail; we use it selectively because it's an extra cost per page.
Why Llama-3 and not GPT-4 or Gemini?
At ~10k invoices/month per client and growing, per-page LLM cost matters. Self-hosted Llama-3 8B on a single L4 GPU handles our throughput at a fraction of API cost, and we keep customer data in our VPC — important for finance docs. We benchmarked GPT-4 and Gemini Pro on the labeled set; both got 1–2 points more accuracy, not enough to justify per-call cost at this volume. If a customer needed higher accuracy and was willing to pay, the architecture is provider-agnostic — change one config to switch.

"Good" is context-dependent: for accounts-payable straight-through processing, the industry benchmark is 85–90% for unstructured invoices. 96% means roughly 4 in 100 invoices need touching — well within an acceptable manual touch rate, and a real improvement over the template-matching baseline that was around 70% on layout-novel invoices.
What about PII? These invoices have account numbers, contact info.
Several controls. Self-hosted Llama-3 keeps content in our VPC — no third-party LLM ingress. Logging redacts known PII patterns (account numbers, IBANs) before persisting to BigQuery — we log the structure, not the values, for analytics. Per-tenant data isolation in the bucket and DB. Access to the exception queue is audited. CMEK on storage. We did a DPIA before launch.

Project 4 — LoRA / QLoRA Experiments

Resume claim: "Experimented with LoRA and QLoRA via Hugging Face Transformers and PEFT for domain-specific document Q&A."
Smaller project on the resume but architecturally interesting — the trap is overclaiming. Be precise about scope.

The problem

For specific document Q&A use cases — internal HR policy queries with very particular phrasing, regulatory document Q&A with exact-citation requirements — base-model RAG gave correct answers but in inconsistent format, occasionally paraphrasing where verbatim was needed, and required long system prompts to enforce style. The hypothesis: a small fine-tune teaches style/format and shortens the system prompt, freeing context for retrieval.

Architecture & flow

LoRA/QLoRA experiment pipeline — data curation, QLoRA training on Vertex AI A100, RAGAS eval, optional adapter merge, Vertex Endpoint serving.

Training data (how it was prepared)

  • Seed: ~500 human-written Q/A pairs from analyst conversations, each with an exact policy citation.
  • Augmentation: GPT-4 was used to generate paraphrased question variants from the seed, each manually reviewed (~1500 additional examples).
  • RAG context attachment: for each Q/A, the gold passage(s) retrieved by our production retriever were attached as context — so the model learns to use given context, not memorize the answer. Without this, the model would learn to ignore context at inference time.
  • Negative examples: ~200 pairs where the answer is "not in the provided context" — to discourage hallucination.
  • Chat template: formatted to Llama-3 instruction template; loss masked on the input tokens (compute loss only on the assistant response).
  • Split: 80/10/10 train/val/test. Test set held out entirely — never used for hyperparameter tuning.

Training setup

  • Base model: meta-llama/Meta-Llama-3-8B-Instruct.
  • Quantization: NF4 with double quant, bf16 compute (QLoRA).
  • LoRA config: r=16, alpha=32, dropout=0.05, targeting all attention projections plus MLP gate/up/down.
  • Optimizer: paged AdamW 8-bit; LR 2e-4 with cosine schedule and 3% warmup.
  • Batch: per-device batch 4, grad accum 8 (effective 32); 3 epochs; early stopping on val loss.
  • Framework: HuggingFace SFTTrainer with peft, bitsandbytes, transformers.
  • Compute: single A100 80GB on Vertex AI Custom Training, ~4 hours per run.
  • Tracking: Weights & Biases — loss curves, sample generations, hyperparameter sweeps.

Evaluation

  • RAGAS faithfulness & answer relevance on the held-out test set.
  • Style/format compliance — regex for citation format + LLM-as-judge for tone match.
  • Compared against (a) base Llama-3 with the same prompt, (b) base Llama-3 with a longer system prompt, (c) GPT-4 with the long prompt.

Findings (be honest)

  • QLoRA fine-tune improved style/format compliance materially — citation format went from ~70% adherence (base + prompt) to ~95% (fine-tuned).
  • Faithfulness / correctness did not significantly improve over base Llama-3 with the same retrieved context — confirming that RAG owns the knowledge, fine-tuning owns the behavior.
  • Shorter system prompt achievable post-fine-tune — net token savings per request.
  • The fine-tune didn't ship to production at scale — we made a pragmatic call that prompt + RAG + structured output covered the gap with less ops burden. The artifact and methodology are reusable for future use cases where the cost calculus differs.

Deployment (what we did / would do)

  • For deployment, we tested two patterns: merged inference (LoRA merged into base, deployed as a single fine-tuned model) and multi-adapter (base model + LoRA loaded as a vLLM adapter, swappable per request). Multi-adapter is the right choice if we have multiple fine-tunes per use case.
  • Vertex AI Endpoint with vLLM custom container, L4 GPU, autoscale 1–3.
  • CI/CD: GitHub Actions trigger on adapter version tag → eval gate → push to Vertex Endpoint with canary.

Q&A drill — LoRA / QLoRA

Walk me through your LoRA hyperparameters.
r=16, alpha=32 (so the effective scaling is alpha/r = 2). Dropout 0.05. Target modules: all four attention projections (q, k, v, o) plus MLP gate/up/down — gives strongest results in literature and we confirmed empirically. Learning rate 2e-4 with cosine schedule — LoRA tolerates much higher LR than full fine-tuning. Three epochs with early stop on val loss; LoRA overfits fast on small datasets so we never went past 3.
Why QLoRA instead of full LoRA?
A100 80GB makes Llama-3 8B fit comfortably with full LoRA — QLoRA wasn't a memory necessity at that scale. We used QLoRA primarily for the reproducibility on smaller GPUs (developers iterating on T4s or L4s) and to validate the workflow before scaling to bigger models like 70B variants where QLoRA becomes essential. Quality difference vs full LoRA on our task was negligible.
Why didn't this ship to production?
A few reasons stacked. (1) Faithfulness — the most business-critical metric — didn't move; only style improved. (2) Operationally, prompt iteration is faster than retraining; the team's velocity on prompt+RAG was higher. (3) Cost of self-hosting at our then-volume didn't beat using Gemini via Vertex. (4) We hadn't built robust A/B infrastructure to roll out a fine-tune safely. We took the learnings and the eval harness; the methodology is on the shelf for use cases where the math will work out — e.g., a hypothetical SaaS where every customer wants their own brand voice, where multi-adapter LoRAs become economically obvious.
What would you do differently if you re-ran this?
Three things. (1) Use DPO on top of SFT — collect preference pairs from analysts (chose A over B) and align style there. SFT alone teaches "what good looks like"; DPO teaches "what's better". (2) Try a much smaller base model (Phi-3 Mini, Llama-3.2 3B) — for this task, the 8B might be overkill and a smaller model fine-tunes faster and serves cheaper. (3) Build the multi-adapter serving infra from day one — even for one customer — so we're ready to scale to many. The biggest mistake was treating the experiment as one-shot rather than building the pipeline as a reusable platform.

SITUATION A junior on my team was assigned to build the validation agent for the invoice pipeline. They were strong at Python but new to LangGraph and agentic patterns.

TASK Get them productive without doing the work for them, and use it as a chance to scale the team's LangGraph expertise.

ACTION I pair-programmed the first state graph with them, then handed off the next two with code review. I shared a "LangGraph for Skeptics" doc I'd written summarizing the mental model — state, nodes, edges, reducers — and ran a 1-hour internal session for the wider team. For their work specifically, I asked questions ("what happens if math check fails AND vendor match fails?") rather than dictating answers, and let them work the design through.

RESULT They shipped the validation agent in six weeks, then took on the synthesis agent independently. Two other team members built LangGraph services in the same quarter — the doc and the session lowered the activation energy. The junior is now the go-to person for LangGraph on a different project. The personal lesson for me: writing the internal doc forced me to make my own implicit knowledge explicit, which made me a better designer.

STAR 5 — Cross-functional / cross-stack work

SITUATION My background is broad — SAP UI5 / ABAP, Java / Spring Boot, Python AI, DevOps with Terraform. On the decarbonization project, the AI/Q&A overlay needed to bridge the Spring Boot backend with the Python AI orchestration team.

TASK Define the contract between the two stacks so neither team blocked the other, and ship the feature on time.

ACTION I proposed a gRPC + protobuf contract between the Spring service and a Python FastAPI agentic service. I wrote the IDL with both teams, drafted the integration tests, and built a stub on each side first so both could develop against the contract in parallel. Where the AI team needed structured emissions data, I implemented BigQuery views in the data layer rather than letting them write raw SQL — a clean boundary.

RESULT Both teams shipped on the same sprint. The gRPC boundary became the template for two further cross-team integrations. The bigger pattern: when teams have different stacks, the contract is the deliverable — owning the interface yourself unblocks both sides.

STAR 6 — Handling ambiguity

SITUATION Early in the LRA project, the DQC rubric was 80 criteria in a spreadsheet with one-line descriptions, inconsistent terminology, and no examples of pass/fail. The business assumed we could "just plug it into AI."

TASK Make this concrete enough to build against, without spending six months in requirements purgatory.

ACTION I sat with two senior reviewers and walked through 10 real reviews, asking "what made this pass?" for each criterion. I built a YAML representation of each criterion with a definition, prompt template, 3 pass examples, 3 fail examples, and a unit test. I then sampled the remaining 70 criteria and grouped them — most fit a small number of patterns (presence, format, alignment, currency, accessibility). The unique ones got bespoke treatment; the rest reused templates.

RESULT The structured rubric became both the prompt source and the eval ground truth. Reviewers could update the YAML themselves — the system improved without engineering involvement. The pattern I took away: ambiguity is often a tooling problem — building the structured artifact is often the fastest path forward, not waiting for the spec.

STAR 7 — A failure you owned

SITUATION Early in the AR Email Agent project, I over-scoped the initial release — I wanted classifier + ERP lookup + drafting + auto-reply all in v1, on a tight deadline.

TASK We hit the deadline only by cutting corners on evaluation. The launch was rocky — accuracy was below target and we had to roll back to classifier-only for a sprint to rebuild trust.

ACTION I owned the call publicly in the retro — I'd traded eval depth for scope, and the trade was wrong. I rebuilt the launch plan as four progressive launches: classifier → classifier+lookup → +draft (human-sent) → +auto-reply, each with a one-sprint canary window and explicit go/no-go metrics. I also instituted a "no auto-action feature ships without an eval gate" rule for the team.

RESULT The phased relaunch hit every quality bar and the auto-reply feature shipped two months later than originally planned but with zero incidents and 55% resolution-time impact. The personal lesson: with agentic systems, evaluation isn't a phase, it's the rails — under-investing in it doesn't save time, it borrows it at high interest.

Red flags — things candidates say wrong

These are the things that make senior interviewers wince. Avoid them, and you signal calibration. Better: gently call them out when you see them happening in someone else's answer.
  • "I used LangChain for everything." → "I use LangChain for composition primitives and LangGraph for orchestration; for simple cases I call the provider SDK directly because the overhead isn't justified."
  • "Just use GPT-4 / Gemini / Claude." → "For this workload I'd benchmark cheap-first; route by complexity; reach for frontier models only on the steps that need them."
  • "We achieved high accuracy." → "On a held-out set of N, we hit X% on metric Y, defined as Z. Here's where it breaks."
  • "We just fine-tuned it." → "We considered fine-tuning, evaluated against RAG and prompt engineering, picked X because Y; here's the cost trade-off."
  • "RAG solves hallucination." → "RAG reduces certain hallucinations by grounding in retrieved context; it introduces new failure modes — retrieval recall gaps, irrelevant chunks, citation fabrication — that need their own evaluation."
  • "We use vector search." → "We use hybrid retrieval — dense plus BM25 with RRF fusion — and reranking; pure vector misses on named entities and exact phrases."
  • "LLMs can do anything now." → "LLMs are non-deterministic next-token predictors that excel at language and pattern transfer; bad at: exact math without tools, novel reasoning beyond training distribution, long-horizon planning without scaffolding."
  • "We don't have evals because it's hard to evaluate." → "We have a 200-example golden set we run nightly, with metrics for X, Y, Z and a regression gate in CI."
  • "I'd build an agent." → "I'd start with the simplest deterministic pipeline; introduce agency only where branching depends on intermediate output."
  • "We don't need to think about cost — tokens are cheap." → "At our QPS, the per-call cost compounds; we monitor $/request, route by complexity, and cache the stable prefix."
  • "We can roll back if something goes wrong." → "We deploy via canary with an automatic rollback trigger on quality regression — not just error rate."
  • "We use MCP because it's the new standard." → "MCP standardizes tool integration so we own the boundary once and reuse across apps; specifically here it gave us X."
  • "Computer use will replace APIs." → "APIs are always preferred when available; computer use fills the gap for systems with no programmatic surface — used sparingly, in sandboxes, with human oversight."
  • Vague stories without numbers or systems thinking. → Always: scope, constraints, alternatives considered, measurable outcome, what you'd change.

Must-know gotcha questions

Consolidated list of trap questions. Have an answer for each ready.
Gotcha 1 "LangChain is bloated and unstable. Do you really use it?"
Answer: Acknowledge the criticism — early LangChain was over-abstracted and APIs broke. Since the v0.1+ refactor (langchain-core / langchain / langchain-community split, LCEL replacing chain hierarchies, LangGraph for stateful flows), the framework is leaner and more stable. I use the parts that earn their place — Runnables, prompt templates, output parsing, provider abstractions — and reach for LangGraph for orchestration. For one-shot LLM calls I use the provider SDK directly.
Gotcha 2 "Why not just use the OpenAI Assistants API or Bedrock Agents and skip LangChain entirely?"
Answer: Managed agent platforms work well when your workflow fits their model — supervisor + tools + retrieval. They get hard when you need fine-grained state control, human-in-the-loop at specific points, multi-agent coordination beyond a single supervisor, or portability across providers. LangGraph gives me explicit control over the state machine; the managed services give me convenience. For most non-trivial enterprise agents I'd still pick LangGraph.
Gotcha 3 "Your RAG system returns wrong answers occasionally. How do you debug?"
Answer: Decompose by stage. Is it (a) a retrieval failure — relevant chunk not retrieved? Check the golden set's context_recall. (b) a ranking failure — relevant chunk retrieved but ranked low? Check the reranker. (c) a generation failure — relevant chunk in context but model ignored it? Check faithfulness, prompt phrasing. (d) a citation failure — answer correct but citation wrong? Compare cited span to source. Each stage has its own metric and fix path. I never debug RAG holistically — I bisect.
Gotcha 4 "Fine-tune or RAG?"
Answer: Mostly RAG. Fine-tune for behavior — style, format, tone, structured output adherence; RAG for knowledge. The two are complementary, not alternatives. I'd fine-tune only when prompting can't get me there at acceptable cost — and even then, prompt caching closes most of the gap in 2025-26.
Gotcha 5 "What chunk size? What top-K?"
Answer: Whatever the golden set says. Strong defaults are 512 tokens / overlap 50–100 / top-K of 5 with reranking from a candidate pool of 30–50. But the right answer is "I evaluate". If you don't have a golden set, build one — 50 examples is enough to start.
Gotcha 6 "Cosine vs dot product vs L2?"
Answer: For unit-normalized embeddings (most modern embedders), cosine and dot product are equivalent. Pick cosine for safety because it normalizes for you. L2 distance is rare in modern RAG.
Gotcha 7 "How do you handle prompt injection?"
Answer: Defense in depth. (1) Separate trusted instructions from untrusted content in the prompt structurally — system vs user, or explicit boundaries. (2) Sanitize / filter known injection patterns at ingress. (3) Treat tool outputs as untrusted — apply the same checks. (4) Principle of least privilege on tools — the agent can't call destructive tools without explicit human approval. (5) Output filtering for leaked instructions. (6) For high-stakes deployments, a separate "validator" LLM verifies the action before execution.
Gotcha 8 "How would you reduce LLM costs by 50%?"
Answer: Layer attack. (1) Prompt cache the stable prefix — system + few-shot — often a 30–50% win immediately. (2) Route by complexity — cheap model for classification/extraction, expensive for synthesis. (3) Shrink context — rerank to fewer chunks, summarize old conversation. (4) Semantic cache for common queries. (5) Move to a cheaper model and validate quality — often a tier-down works fine. (6) Self-host open models if QPS is high and consistent. (7) Batch where possible. (8) Set hard token budgets per request.
Gotcha 9 "Your agent occasionally loops forever. How?"
Answer: First, circuit breakers: max iterations, max identical consecutive tool calls. Then root-cause from traces — usually it's tool output ambiguity (the model doesn't know whether the call succeeded), bad tool descriptions, or a stop-condition the model can't satisfy. Fixes are in the tool layer 80% of the time, not the agent loop.
Gotcha 10 "What's the difference between memory and a checkpointer?"
Answer: Classic LangChain Memory classes are conversation-history buffers — they shape what goes into the next prompt. A LangGraph checkpointer is full state persistence — every node execution snapshots the entire graph state to a backend, enabling resume, HITL, time travel, and conversation memory all at once. Modern systems use checkpointers; memory is the older pattern.
Gotcha 11 "How do you A/B test prompts in production?"
Answer: Configurable runnables (or feature flags) route a percentage of traffic to the new prompt. Tag traces with the variant. Run offline eval (golden set) for the new prompt before any production exposure — that's the quality gate. Online, monitor user signals (thumbs, abandonment) and your faithfulness sample over the variant cohort. Promote the variant if it beats baseline by a configured margin over a configured window.
Gotcha 12 "How do you evaluate an agent (not just a chain)?"
Answer: Three layers. (1) Per-step: did each tool call produce the right output? Was the right tool chosen? (2) Trajectory: did the agent take a reasonable path, or did it wander? (3) End-to-end: did the final answer satisfy the user goal? Each needs its own dataset — step-level uses synthetic or labeled tool call examples; trajectory uses LLM-as-judge on traces; end-to-end uses outcome labels. LangSmith and Vertex AI Gen AI Evaluation have built-in primitives for each.
Gotcha 13 "Why did you choose LoRA r=16?"
Answer: Empirically. r=8/16/32 typically span the useful range; r=16 with alpha=32 is a strong default with modest parameter count. I ran sweeps; r=8 underfit on harder examples, r=32 didn't help and increased train time. The right answer is always "I tried a few and measured", not a single magic number.
Gotcha 14 "What's the difference between RLHF and DPO?"
Answer: RLHF is three stages — SFT, reward model training on preference pairs, RL (PPO) against the reward model with KL penalty. DPO reparameterizes the objective so you can directly optimize the policy from preference pairs with a simple classification loss — no separate reward model, no PPO. DPO is simpler, more stable, comparable results, and is the default starting point in 2025-26 unless you specifically need an interpretable reward signal or online RL.
Gotcha 15 "MCP vs function calling — same thing?"
Answer: Different layers. Function calling is the model capability — the LLM emits structured tool calls. MCP is the transport — a standardized protocol for how applications discover and invoke tools from external servers. An MCP server's tools ultimately get exposed to the model via function calling. MCP also covers resources (read-only data) and prompts (reusable templates), which function calling alone doesn't.
Gotcha 16 "Should every step in an agent be an LLM call?"
Answer: Definitely not. Deterministic code beats LLM calls everywhere it can — faster, cheaper, more reliable. Use LLMs for the steps that genuinely need language understanding or generation; use code for everything that has a clear rule. The art of designing an agent is putting boundaries between the two.
Gotcha 17 "If your model provider goes down, what happens?"
Answer: .with_fallbacks() to a second provider. If providers are abstracted via a gateway (LiteLLM, Portkey), the gateway handles routing and circuit breaking. For mission-critical paths, multi-provider active-active. Worst case, degrade — return a "service temporarily unavailable, your request is queued" UX rather than nothing.

Quick glossary — terms you must know cold

Skim this the morning of the interview. Each entry is one sentence — enough to recognize and discuss when raised.
TTFT
Time To First Token. The latency between request submission and the model emitting its first output token. Target < 800ms for chat UIs; the perceived-latency metric that matters most.
KV cache
The stored key/value attention tensors for each token already processed; reusing it makes prefill skippable for the matching prefix. Prompt caching (Anthropic, OpenAI) exposes this to API users.
PagedAttention
vLLM's memory layout: the KV cache is paged like virtual memory, eliminating fragmentation and dramatically increasing concurrent sequences per GPU.
Continuous batching
vLLM/TGI scheduling — finished sequences are dropped and new ones added every step, keeping the GPU saturated. 5–24x throughput vs static batching.
Speculative decoding
Small "draft" model proposes N tokens; large model verifies in one forward pass. 2–3x throughput when draft and target agree often.
HNSW
Hierarchical Navigable Small World graph index for ANN. Fast queries, high RAM, slow builds. Modern default.
IVF / IVFPQ
Inverted-file ANN indexes. IVF clusters vectors; IVFPQ adds product quantization for low memory at accuracy cost.
ScaNN
Google's tree-AH hybrid ANN. Powers Vertex AI Vector Search.
RRF
Reciprocal Rank Fusion: score = Σ 1/(k + rank_i). Combine rankings from dense + sparse retrieval; no calibration needed.
HyDE
Hypothetical Document Embeddings. Have the LLM write a hypothetical answer to the query; embed the hypothetical for retrieval. Often beats raw query embedding on short queries.
Reranker
Cross-encoder that scores (query, doc) pairs jointly — slower than bi-encoder similarity but much more accurate. Cohere Rerank v3, BGE-reranker-v2.
RAGAS
Python library of LLM-as-judge metrics for RAG: faithfulness, context_precision, context_recall, answer_relevance.
Faithfulness
Fraction of claims in the generated answer that are supported by the retrieved context. The main hallucination metric.
Context precision / recall
Precision: are retrieved chunks relevant? Recall: did retrieval get all needed info?
SFT
Supervised Fine-Tuning: train on (input, output) pairs to adapt a base model to a task.
PEFT
Parameter-Efficient Fine-Tuning: update small subset of params (LoRA, adapters, prefix tuning) instead of full weights.
LoRA
Low-Rank Adaptation: approximate weight update ΔW as B·A with rank r ≪ original dim. Trains <1% of params, comparable quality.
QLoRA
LoRA + 4-bit NF4 base + double quantization + paged optimizers. Fits 70B on consumer GPUs.
NF4
NormalFloat 4-bit: information-theoretically optimal 4-bit quantization for normally-distributed weights. From the QLoRA paper.
RLHF
Reinforcement Learning from Human Feedback: SFT → reward model → PPO. Aligns models with human preferences. Complex.
DPO
Direct Preference Optimization: reparameterizes RLHF so you can train directly on preference pairs with a simple loss. Simpler, more stable, comparable results.
ORPO / KTO / SimPO
DPO variants. ORPO combines SFT + preference in one stage; KTO uses binary signals; SimPO drops the reference model.
MCP
Model Context Protocol (Anthropic, 2024): open client-server protocol for LLM apps to access tools, resources, prompts. The standardization layer for tool integration.
A2A
Agent-to-Agent protocol (Google, 2025): standardized agent-agent communication. Complementary to MCP (agent-tool).
ReAct
Reasoning + Acting pattern: interleave LLM thoughts with tool actions. Mostly superseded by native tool calling in modern models.
ToT
Tree of Thoughts: branching exploration of multiple reasoning paths, then select. Inference-time compute pattern.
MoE
Mixture of Experts: model with many "expert" sub-networks; router picks a few per token. Massive params, modest active compute. Mixtral, DeepSeek, GPT-4 (rumoured).
Constitutional AI
Anthropic's alignment method: model critiques and revises its own outputs against a set of principles instead of pure human preference labels.
Function calling / Tool use
Model capability to emit structured tool invocations the host application executes. Replaces ReAct prompting in modern models.
Structured outputs
Provider feature constraining model output to a JSON schema (OpenAI Structured Outputs, Anthropic strict tool use, Gemini controlled generation). Eliminates malformed-JSON failures.
Guardrails
Pre/post-processing filters: content moderation, PII redaction, topic restrictions. Bedrock Guardrails, NVIDIA NeMo Guardrails, custom layered approaches.
Prompt caching
Provider feature that caches the KV state of a stable prompt prefix; cached tokens are charged at 10–50% of normal price. Anthropic up to 90% off; OpenAI ~50% off.
Long context
Models supporting very large input windows (Gemini 1–2M, Claude 200k, GPT-4.1 1M). Enables LRA — retrieve more, let the model reason over more.
LRA
Long-context RAG: RAG that exploits long-context models — retrieve broadly, fit it all in context, let the model synthesize. Your flagship pattern.
GraphRAG
RAG over a knowledge graph extracted from documents. Strong for global / multi-hop questions; expensive to build.
Agentic RAG
RAG where an agent iteratively retrieves and refines, not one-shot. Self-RAG, CRAG, RAG-Fusion are named variants.
Self-RAG / CRAG
Self-RAG: model emits reflection tokens deciding when to retrieve. CRAG (Corrective RAG): retrieve → grade → fallback to web if low confidence.
RAG-Fusion
Multi-query rewriting + RRF fusion of retrieval results across queries.
Computer use
Model trained to view screenshots and emit mouse/keyboard actions. Anthropic Oct 2024; OpenAI Operator, Google Mariner followed. Sandbox required.
Claude Skills
Anthropic Oct 2025: folders of instructions / scripts / resources the model invokes. Complement to MCP; reduces system-prompt bloat.
Extended thinking
Anthropic feature where Claude reasons in a hidden scratchpad before responding. Comparable to OpenAI o-series reasoning.
vLLM
Open-source LLM inference server: PagedAttention + continuous batching. Default for self-hosting open-weight models.
TGI
Text Generation Inference (Hugging Face): open-source serving with continuous batching.
SGLang
Structured generation runtime with RadixAttention (prefix sharing across requests). Strong for agentic workloads with repeated prefixes.
PagedAttention
vLLM's virtual-memory-style KV cache layout enabling near-zero fragmentation.
WIF
Workload Identity Federation: GCP feature exchanging external identities (GitHub Actions OIDC) for short-lived GCP credentials. Replaces long-lived JSON keys.
VPC-SC
VPC Service Controls: GCP perimeter around services like Vertex AI / BigQuery. Prevents data exfiltration even with valid IAM.
CMEK
Customer-Managed Encryption Keys: bring-your-own-key encryption for GCP/AWS services. Required for regulated data.
DLP
Data Loss Prevention: scanning to detect/redact PII, credentials, secrets. Cloud DLP / Amazon Macie.
DPIA
Data Protection Impact Assessment: GDPR requirement for high-risk processing. AI systems usually trigger one.
Token budget
Hard cap on tokens per request to bound cost and latency. Implemented at the chain/agent layer.
Semantic cache
Cache that retrieves by embedding similarity (not exact match). Hits near-duplicate queries. Watch: cross-tenant leakage if cache key doesn't include tenant.
Prompt injection
Adversarial input that hijacks the LLM's instructions. Defense: structural separation, output filtering, least-privilege tools, validator LLMs.
Confused deputy
Security pattern where a privileged agent is tricked into acting on behalf of an attacker. Mitigation: capability scoping per request, user consent for sensitive ops.
Golden set
Curated evaluation dataset with labeled inputs/outputs. The ground truth for regression testing. 50–200 examples is enough to start; version it in git.
LLM-as-judge
Using a model to grade outputs against criteria. Cheap, scalable, biased. Calibrate against human labels; use for trends not absolute scores.
Shadow deployment
Running a new model alongside production, comparing outputs without serving the new one to users. Risk-free validation.
Canary
Route a small % of real traffic to the new version; monitor; ramp on success, rollback on regression.
